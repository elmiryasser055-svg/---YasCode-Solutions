## 0. تكييف مهم: من "نشر خادم" إلى "تعبئة تطبيق Desktop"

القالب الأصلي يفترض `Dockerfile`/استضافة (VPS/Vercel/AWS). بما أن هذا **تطبيق Electron يعمل بالكامل على جهاز المالك، بلا خادم وبلا اتصال إنترنت دائم**، لا يوجد "نشر" بالمعنى التقليدي. إليك التكييف الكامل، بنفس منطق الجدول المستخدم في `back-end.md` § 0:

| المفهوم التقليدي | المكافئ هنا | لماذا |
|---|---|---|
| `Dockerfile` / نشر على خادم | **`electron-builder`** ينتج ملف `.exe` (installer) | لا خادم يُشغَّل؛ "النشر" = تثبيت التطبيق على جهاز المستخدم مباشرة |
| اختيار استضافة (VPS/AWS...) | ⚪️ **غير قابل للتطبيق** | لا يوجد أي مكوّن يحتاج استضافة — قاعدة البيانات SQLite محلية والتطبيق كامل ضمن العملية |
| `docker-compose` لتشغيل DB محليًا | ⚪️ **غير قابل للتطبيق** | SQLite ملف واحد مدمج، لا خادم قاعدة بيانات منفصل يحتاج تشغيله |
| CI/CD لنشر على خادم | CI/CD **لبناء installer** ورفعه كـ GitHub Release | نفس الفكرة (أتمتة + عدم التدخل اليدوي) لكن الناتج ملف تثبيت لا نشر مباشر |
| Environment variables على الخادم | `.env` محلي وقت التطوير فقط؛ في الإنتاج القيم الافتراضية مدمجة عبر `app.getPath("userData")` | لا "خادم إنتاج" لضبط متغيرات بيئة عليه |
| Monitoring/logging بعد الإطلاق (APM, Sentry...) | ملف log محلي + زر "تصدير السجلات" داخل التطبيق | لا اتصال إنترنت دائم يسمح بإرسال تتبع عن بُعد تلقائيًا |

## 1. التعبئة (Packaging) — بديل Dockerfile هنا

**الأداة: `electron-builder`** — الخيار المعياري لتحويل تطبيق Electron إلى installer قابل للتوزيع، مع دعم ممتاز لـ Windows تحديدًا (NSIS installer).

إعداد التعبئة كامل داخل `package.json` (حقل `build`) — راجع الملف المرفق. أهم النقاط:

- **`asarUnpack`** إجباري لملفين تحديدًا: `better-sqlite3` (مكتبة native تحتاج ملف `.node` مُصرَّف، لا يعمل داخل أرشيف `asar` المضغوط) و`drizzle/migrations` (يجب أن تبقى ملفات SQL خام قابلة للقراءة عند الإقلاع لتطبيق `migrate()` في `lib/db.ts`، راجع المرحلة 3)
- **`node-thermal-printer`** يعتمد أيضًا على وصول مباشر لمنافذ USB/نظام التشغيل — يُختبر إلزاميًا على جهاز Windows فعلي قبل كل إصدار (ليس كافيًا الاختبار على بيئة CI فقط)
- **Native rebuild:** `better-sqlite3` يحتاج إعادة تصريف (`electron-rebuild` أو `@electron/rebuild`) ليتوافق مع إصدار Node/Electron المُستخدم — يُضاف كخطوة `postinstall` في `package.json`:
  ```json
  "postinstall": "electron-rebuild -f -w better-sqlite3"
  ```

## 2. خيار الاستضافة — لماذا "لا استضافة" هو القرار الصحيح هنا

بما أن المشروع (حسب المرحلة 1) **مستخدم واحد، جهاز واحد، بلا حاجة لمزامنة سحابية أو وصول عن بُعد**، أي استضافة (VPS/AWS...) ستكون تعقيدًا وتكلفة بلا أي فائدة فعلية — **القرار الصحيح هو التوزيع المباشر لملف `.exe`** عبر:
- تحميل مباشر (رابط GitHub Release أو أي تخزين ملفات بسيط) يُثبَّته المالك بنفسه، أو
- نسخ الملف عبر USB إن كان جهاز المحل بلا إنترنت إطلاقًا وقت التثبيت الأول

**إن تغيّر هذا مستقبلاً** (مثلاً: المالك يريد لاحقًا لوحة تحكم عن بُعد أو نسخ بين عدة أجهزة)، عندها فقط تُعاد مناقشة إضافة مكوّن خادم/استضافة — وهذا خارج نطاق المتطلبات الحالية عمدًا.

## 3. متغيرات البيئة وإدارتها بأمان

| المتغيّر | وقت التطوير | وقت الإنتاج (exe مثبَّت) |
|---|---|---|
| `NODE_ENV` | `development` في `.env` | `production` (مضمّن تلقائيًا بواسطة electron-builder، لا حاجة لضبط يدوي) |
| `DB_PATH` | مسار محلي اختياري للتجربة | **غير مضبوط يدويًا** — القيمة الافتراضية في `lib/env.ts` تستخدم `app.getPath("userData")` تلقائيًا، فكل جهاز تثبيت يحصل على مسار صحيح خاص به |
| `LOCAL_ENCRYPTION_KEY` | فارغ ما لم تُستخدم ميزة تشفير النسخ الاحتياطي | نفسه — ميزة مستقبلية غير مفعّلة حاليًا |
| `DEFAULT_EXPIRY_WARNING_DAYS` | حسب الحاجة للاختبار | القيمة الافتراضية 30 يومًا، قابلة للتعديل لاحقًا من شاشة الإعدادات داخل التطبيق (`app_settings`، راجع schemaDB.md) وليس عبر متغير بيئة يُعاد بناء التطبيق من أجله |

**القاعدة الذهبية:** `.env` **لا يُضمَّن أبدًا** في نسخة exe النهائية (`electron-builder` لا يحزم ملفات خارج `files`/`extraResources` المحددة صراحة في `package.json`، و`.env` ليس من بينها) — راجع `.env.example` المرفق كنموذج فارغ من أي قيمة حقيقية.

## 4. استراتيجية CI/CD

CI/CD هنا هدفه **أتمتة بناء الـ installer فقط**، وليس نشرًا فعليًا (لا يوجد خادم إنتاج يُنشر عليه تلقائيًا — التثبيت خطوة يدوية من المالك دائمًا، وهذا مقصود ومناسب لحجم المشروع).

راجع `.github/workflows/build-release.yml` المرفق — يعمل تلقائيًا عند دفع tag بصيغة `vX.Y.Z`:
1. تثبيت التبعيات + تشغيل الاختبارات (unit tests من `back-end.md`/`front-end.md`)
2. `npm audit` (تنبيه وليس إيقاف تلقائي — القرار النهائي بمراجعة يدوية قبل كل إصدار، حسب متطلب "Dependency Security" من المرحلة 3)
3. توليد/توثيق أي migration جديد
4. بناء الـ installer عبر `electron-builder` على بيئة **Windows فعلية** (`windows-latest` — إجباري بسبب `better-sqlite3`/`node-thermal-printer` كما ذُكر في § 1)
5. رفع ملف `.exe` الناتج تلقائيًا كـ GitHub Release

**Code signing (اختياري حاليًا):** بدون توقيع رقمي، Windows SmartScreen سيُظهر تحذير "ناشر غير معروف" عند أول تشغيل — مقبول لمشروع بمستخدم واحد يعرف مصدر الملف، لكن يُنصح بشهادة توقيع لاحقًا إن اتسع التوزيع. الإعداد جاهز مسبقًا في الـ workflow (متغيرات `CSC_LINK`/`CSC_KEY_PASSWORD` عبر GitHub Secrets، بنفس مبدأ Secrets Management من `back-end.md`).

## 5. خطة الـ Database Migrations عند النشر

مُطبَّقة بالفعل في `lib/db.ts` (المرحلة 3)، أُلخّصها هنا من زاوية "النشر":

1. عند كل تشغيل للتطبيق (بما فيه أول تشغيل بعد تحديث لنسخة exe جديدة)، `initDatabase()` يتحقق تلقائيًا من وجود migrations لم تُطبَّق بعد
2. **قبل** تطبيق أي migration: نسخة احتياطية فورية من ملف `.sqlite` بامتداد `.bak-{timestamp}` — إن فشل الـ migration لأي سبب، بيانات المالك سليمة 100%
3. الـ migrations نفسها (ملفات SQL) تُحزَّم داخل الـ installer عبر `extraResources` (راجع `package.json` § build)، وتُطبَّق **محليًا دون أي اتصال إنترنت**
4. **لا خطوة يدوية مطلوبة من المالك إطلاقًا** — يفتح التطبيق بعد التحديث، وتُطبَّق كل التغييرات تلقائيًا خلف الكواليس

## 6. أساسيات المراقبة والـ Logging بعد الإطلاق

بما أن لا اتصال إنترنت دائم (قرار المرحلة 1)، **لا يوجد** حل مراقبة عن بُعد تقليدي (Sentry، Datadog...) قابل للتطبيق فعليًا هنا دون إعادة نظر في قرار offline-first بالكامل. البديل العملي:

- **`lib/logger.ts`** (مبني في المرحلة 3) يكتب كل خطأ تقني كامل في `{userData}/logs/app.log` محليًا
- **يُوصى بإضافة زر "تصدير السجلات"** في شاشة الإعدادات (front-end، تطوير لاحق بسيط): يضغط عليه المالك إن واجه مشكلة، فيُنسخ ملف الـ log الحالي لسطح المكتب ليُرسله للدعم الفني يدويًا (بريد إلكتروني، واتساب...) — هذا يعوّض غياب تتبع الأخطاء التلقائي عن بُعد
- **Electron `crashReporter`:** يمكن تفعيله لحفظ crash dumps محليًا فقط (`submitURL` غير مضبوط = لا إرسال تلقائي لأي خادم خارجي، متوافق تمامًا مع قرار offline-first)
- **مراقبة حجم قاعدة البيانات ومجلد backups:** يُنصح بتنبيه بسيط داخل التطبيق إن تجاوز حجم `{userData}` حدًا معينًا (مثال: 500 ميجابايت) لتذكير المالك بتنظيف نسخ احتياطية قديمة يدويًا، رغم أن `lib/backup.ts` (المرحلة 3) يحذف تلقائيًا ما يتجاوز 30 نسخة

**إن تغيّر قرار offline-first مستقبلاً** (مثلاً المالك يوافق على اتصال إنترنت جزئي للتحديثات فقط)، عندها يصبح دمج أداة مراقبة أخطاء سحابية خفيفة (مثل Sentry في وضع "أخطاء فقط") خيارًا يستحق إعادة النظر فيه.

## 7. قائمة تحقق قبل كل إصدار جديد (Release Checklist)

1. ✅ الاختبارات (unit + integration من `back-end.md`، component + E2E من `front-end.md`) خضراء بالكامل
2. ✅ `npm audit` رُوجع يدويًا، لا ثغرات حرجة غير معالجة
3. ✅ اختُبرت الطباعة (ESC/POS) وقارئ الباركود على جهاز Windows فعلي — ليس فقط بيئة CI
4. ✅ رقم الإصدار (`version` في `package.json`) حُدِّث، والـ tag المدفوع مطابق له
5. ✅ إن وُجد migration جديد: اختُبر على نسخة من قاعدة بيانات حقيقية (نسخة من بيانات المحل الفعلية، وليس قاعدة فارغة فقط) قبل الدفع
